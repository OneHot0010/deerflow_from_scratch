# Aegis 中间件（Middleware）设计、应用与实现详解

> 目标读者：需要理解或扩展 `tob_audit_agent` 后端 Agent 运行时的开发者。
> 分析范围：`backend/packages/harness/aegis/agents/middlewares/` 目录下的全部中间件，以及它们在 `lead_agent/agent.py` 中的装配方式。

---

## 一、为什么需要"中间件"

Aegis 的 Agent 主体是基于 **LangChain Agent + LangGraph** 的一个 ReAct 风格循环：

```
before_agent → (before_model → wrap_model_call → after_model)
             → wrap_tool_call → 循环
             → after_agent
```

在这条主链路两侧，Aegis 面对的却是"企业级 Agent 平台"层面的一系列横切问题：

- **上下文管理**：如何注入用户上传文件、如何在长会话中做摘要、如何在总结丢失关键信息前进行救援？
- **可靠性**：如何应对 LLM 抖动/超时？如何处理工具执行中的异常与中断？
- **可观测性**：token 用量、工具耗时、审计日志如何统一采集？
- **安全**：如何在 bash 工具执行前做命令级审计？
- **交互**：模型问澄清、生成图片、需要弹出待办列表等，如何统一挂到主循环之外？

如果把这些能力全部塞进 `agent.py`，业务逻辑会被彻底吞没。Aegis 采用 LangChain 的 **AgentMiddleware** 抽象，让每个横切关注点都成为**可独立编写、可独立测试、可动态启用**的一层，最终由 `_build_middlewares()` 组装成链条。

**中间件的本质**：一组以特定生命周期钩子（hook）为约束的可插拔类，围绕 Agent 的一次执行（run）依次拦截、观察、改写 state / request / result。

---

## 二、LangChain AgentMiddleware 的 5 个 Hook 点

Aegis 里几乎所有中间件都继承自 `langchain.agents.middleware.AgentMiddleware[<State>]`，并根据自身职责实现其中一个或多个 hook（每个 hook 都有同步版和 `a` 前缀的异步版）：

| Hook | 触发时机 | 典型用途 |
|---|---|---|
| `before_agent` / `abefore_agent` | 整个 Agent 运行的最开始，仅一次 | 解析 thread/owner 上下文、注入上传文件说明、启动分布式活跃标记 |
| `before_model` / `abefore_model` | 每次调 LLM 之前 | 摘要压缩历史、注入图片内容、注入 todo 提醒 |
| `wrap_model_call` / `awrap_model_call` | 包裹 LLM 调用本身，可捕获异常/改写 request | LLM 重试与熔断、注入 owner 自定义 skills 到 system prompt、修补 dangling tool_call |
| `after_model` / `aafter_model` | LLM 每次返回之后 | 记录 token 用量、生成 thread title、检测循环、Todo 完成度校验 |
| `wrap_tool_call` / `awrap_tool_call` | 包裹每一次工具调用 | Bash 安全审计、tool 异常转 ToolMessage、发流式进度事件、拦截 `ask_clarification` |
| `after_agent` / `aafter_agent` | 整个 Agent 运行结束时 | 释放分布式活跃标记 |

**关键约定**：
- Hook 返回 `dict` → 会被 merge 进 LangGraph 的 state；返回 `None` → 不修改 state。
- Hook 可返回带 `jump_to` / `goto` 的 `Command` 对象，直接改变图的流向（例如强制回到 model 节点、或跳到 `END`）。
- `wrap_*` 类 hook 收到 `handler`（下一层链的入口）和 `request`，必须显式 `handler(request)` 才会真正调用；这正是它可以"重试、改写、短路"的关键。

## 三、Aegis 中间件目录结构

`backend/packages/harness/aegis/agents/middlewares/` 下现有 16 个中间件文件（另外 `aegis/sandbox/middleware.py` 提供 `SandboxMiddleware`）。按职责聚类如下：

| 类别 | 中间件 | 主要 Hook |
|---|---|---|
| 上下文/环境 | `ThreadDataMiddleware`、`SandboxMiddleware`、`UploadsMiddleware`、`OwnerActivityMiddleware` | `before_agent` |
| System Prompt | `OwnerSkillsMiddleware` | `wrap_model_call` |
| 历史压缩 | `AegisSummarizationMiddleware` | `before_model` |
| 规划辅助 | `TodoMiddleware`（继承自 `TodoListMiddleware`） | `before_model` / `after_model` |
| 元数据/观测 | `TokenUsageMiddleware`、`TitleMiddleware` | `after_model` |
| 可靠性 | `LLMErrorHandlingMiddleware`、`ToolErrorHandlingMiddleware`、`DanglingToolCallMiddleware`、`LoopDetectionMiddleware` | `wrap_model_call` / `wrap_tool_call` / `after_model` |
| 安全审计 | `SandboxAuditMiddleware` | `wrap_tool_call` |
| UI/交互 | `ToolProgressMiddleware`、`ViewImageMiddleware`、`ClarificationMiddleware` | `wrap_tool_call` / `before_model` |

## 四、装配顺序：`lead_agent/agent.py` 里的组装逻辑

装配位于 `_build_middlewares()`，它先复用 `build_lead_runtime_middlewares()`（`tool_error_handling_middleware.py` 中定义的共享基线），再叠加 Lead Agent 专属的中间件。**顺序是精心设计的，不是随意堆叠**：

```python
def _build_middlewares(config, model_name, agent_name=None, ...):
    middlewares = build_lead_runtime_middlewares(lazy_init=True)
    #  ↳ 展开后为：
    #    ThreadDataMiddleware        # ① 解析 thread_id/owner 上下文
    #    OwnerActivityMiddleware     # ② 分布式活跃标记
    #    UploadsMiddleware           # ③ 注入上传文件说明
    #    SandboxMiddleware           # ④ 沙箱懒加载
    #    DanglingToolCallMiddleware  # ⑤ 补齐历史里悬挂的 tool_call
    #    LLMErrorHandlingMiddleware  # ⑥ LLM 重试/熔断
    #    SandboxAuditMiddleware      # ⑦ bash 命令审计
    #    ToolProgressMiddleware      # ⑧ 工具进度流事件
    #    ToolErrorHandlingMiddleware # ⑨ 工具异常兜底

    middlewares.append(OwnerSkillsMiddleware(...))        # ⑩ 每次调 LLM 重建 system prompt
    middlewares.append(AegisSummarizationMiddleware(...)) # ⑪ 历史摘要（含 skill 救援）
    middlewares.append(TodoMiddleware(...))               # ⑫ 计划模式
    middlewares.append(TokenUsageMiddleware())            # ⑬ token 用量日志
    middlewares.append(TitleMiddleware())                 # ⑭ 会话标题
    middlewares.append(ViewImageMiddleware())             # ⑮ 视觉模型注入图片
    middlewares.append(LoopDetectionMiddleware())         # ⑯ 循环检测
    # ...custom middlewares（业务扩展点）
    middlewares.append(ClarificationMiddleware())         # ⑰ 澄清最后拦截，永远在末尾
```

`agent.py` 文件顶部注释里明确写下的顺序规则（原文摘自 `lead_agent/agent.py`）：

- `ThreadDataMiddleware` 必须在 `SandboxMiddleware` 之前 —— 后者依赖前者填充的 `thread_id`。
- `UploadsMiddleware` 在 `ThreadDataMiddleware` 之后 —— 上传文件路径依赖 thread 上下文。
- `DanglingToolCallMiddleware` 要在模型看到消息历史之前修补。
- `SummarizationMiddleware` 应尽量靠前，先把上下文压小再走其他处理。
- `TodoListMiddleware` 在 `ClarificationMiddleware` 之前。
- `TitleMiddleware` 在首轮交换完成后触发。
- `ViewImageMiddleware`、`ToolErrorHandlingMiddleware` 都在 `ClarificationMiddleware` 之前。
- `ClarificationMiddleware` **一定放最后**，负责最终截胡 `ask_clarification`。

这条链条的核心哲学：**先建环境 → 再修补历史 → 再压缩历史 → 再重建 prompt → 最后模型/工具执行前的观测与拦截**。

## 五、逐个中间件详解（附代码片段与场景）

以下按照装配顺序，挑出每个中间件的**职责、Hook、实现要点、在 Aegis 中的具体场景**四要素。

### 5.1 `ThreadDataMiddleware`（上下文根基）

**职责**：为整个 Agent Run 解析 `thread_id`、`owner` 身份，并把关键路径（`workspace_path` / `uploads_path` / `outputs_path`）写进 state 的 `thread_data`。

**Hook**：`before_agent`。

**实现要点**：
- 从 `runtime.context` 或 LangGraph `config.configurable` 双重解析 `thread_id`，缺失即抛错，确保下游任何依赖 thread_id 的中间件都拿得到。
- 支持两种模式：
  - **AIO 沙箱模式**：路径都在沙箱内 (`/mnt/uploads`、`/mnt/state`)，中间件只做元数据记录，不再在宿主机上落盘。
  - **Legacy 模式**：仅计算路径字符串，也**从不主动创建** host 目录（避免污染宿主）。
- 同时会在会话首条 `HumanMessage` 前注入 `<session thread_id="..."/>` 标记（一次性），让模型知道自己服务的是哪个 thread，从而正确访问 `/mnt/uploads/{thread_id}/`。

**为什么放第一**：几乎所有后续中间件（Uploads、Sandbox、Summarization 的钩子事件、Audit 日志）都需要 thread_id。

### 5.2 `OwnerActivityMiddleware`（分布式活跃标记）

**职责**：整个 Agent Run 期间在 Owner Sandbox Registry 上维护一枚"我在忙"的分布式标记，防止其它进程回收正在使用的沙箱。

**Hook**：`abefore_agent` / `aafter_agent`。

**实现要点**：
- `abefore_agent` 通过 `OwnerActivityRegistry.begin(...)` 注册活跃标记，并派发一个后台 `asyncio.Task` 定期 heartbeat（周期 = `ttl_seconds / 3`）。
- `aafter_agent` 取消心跳任务、执行 `registry.end(...)` 释放标记。
- 每个 run 只挂一枚活跃标记（以 `run_id` 或 `thread_id` 作为 key）。

**场景**：多个 Agent 请求可能命中同一 Owner 的沙箱，此机制让沙箱回收器不会在 Agent 还在跑的时候把沙箱冷却下线。

### 5.3 `UploadsMiddleware`（上传文件注入）

**职责**：把用户在当前消息里刚上传的文件、以及历史累积的文件，用 `<uploaded_files>` XML 块拼接进最后一条 `HumanMessage` 的开头。

**Hook**：`abefore_agent`。

**实现要点**：
- 新文件来自当前 `HumanMessage.additional_kwargs["files"]`；历史文件走 AIO 的 `list_upload_records_async` 或本地上传目录扫描。
- 对新文件尝试用 `_extract_outline_for_file` 从伴生 `.md` 中抽出标题大纲，追加为「Document outline」段，或退化为前几行内容预览。
- 历史文件用"文件名列表 + 上传目录指针"的紧凑格式呈现，避免 block 无限增长。
- 生成的 block 明确告诉模型："优先用 `read_file` / `grep` / `glob` 处理这些文件，实在不够再上网搜"。

**在项目中的表现**：这是 tob_audit_agent 面对"审计文档 PDF / Excel / Markdown"类任务时的核心入口 —— 用户拖入文件后，Agent 首轮就能看到文件路径与结构，无需人工提示。

### 5.4 `SandboxMiddleware`（沙箱懒加载）

**职责**：在首次工具调用前获取（或复用）对应 Owner 的沙箱句柄，写进 state 的 `sandbox` 字段。

**Hook**：`before_agent`（`lazy_init=False`）或首次工具调用（`lazy_init=True`，Aegis 默认）。

**实现要点**：
- 沙箱在多轮之间**复用**、不在单轮结束时释放，避免频繁冷启动开销。
- 通过 `runtime.context.sandbox_acquire_context` 或 mapping 反序列化后拿到 `SandboxAcquireContext`。
- 应用退出时通过 `SandboxProvider.shutdown()` 统一清理。

### 5.5 `DanglingToolCallMiddleware`（历史修补）

**职责**：扫描 message 历史，把"AIMessage 里发起了 tool_call 但没有对应 ToolMessage"的悬挂调用补上占位 ToolMessage，让 LLM 收到格式合法的对话。

**Hook**：`wrap_model_call` / `awrap_model_call`（不是 `before_model`，是为了确保占位符插在**紧跟发起 tool_call 的 AIMessage 之后**的正确位置，而不是被 `add_messages` reducer 追加到末尾）。

**实现要点**：
- 对 `raw_tool_calls`（provider 原始字典格式）与 `tool_calls`（LangChain 规范化字段）双路兼容。
- 只对当前 request 的 `messages` 做副本改写，不修改真正的 state。

**场景**：用户中途取消请求 / 系统重启后恢复历史时，AIMessage 携带的 tool_call 若丢了配对的 ToolMessage，OpenAI / Anthropic API 会直接报 400。此中间件先行填坑再让 model 看到，是保证「断线续跑」稳定性的关键。

### 5.6 `LLMErrorHandlingMiddleware`（LLM 重试 + 熔断）

**职责**：包裹 LLM 调用，做**指数退避重试**和**熔断降级**，并把不可恢复错误转成一条面向用户的 `AIMessage`。

**Hook**：`wrap_model_call` / `awrap_model_call`。

**实现要点**：
- **错误分类**：透过异常类名（`APITimeoutError` / `APIConnectionError` / `InternalServerError` / `ReadError` / `RemoteProtocolError`）、HTTP 状态码（`{408, 409, 425, 429, 500, 502, 503, 504}`）以及正则匹配（"quota / auth / busy" 等中英文关键词）判定 `retriable + reason`。
- **重试策略**：默认 3 次；`Retry-After` / `Retry-After-Ms` 响应头存在时优先使用它决定 wait；否则指数退避 `1s → 2s → 4s → 8s`（`retry_cap_delay_ms` 上限）。
- **熔断（Circuit Breaker）**：
  - `closed` → 连续失败达阈值（默认 5）→ `open`（默认 60s 冷却）。
  - 冷却期结束进入 `half_open`，允许一个探测请求：成功→`closed`；失败→回 `open`。
  - `open` 状态直接返回熔断提示 `AIMessage`，不再打后端。
- 通过 `stream_writer` 主动推送 `llm_retry` 自定义事件，前端可实时展示"第 N/M 次重试"。

**场景**：面向 LLM 网关或第三方 API 抖动、限流的常规防御，是让长时间对话不因偶发抖动整体失败的底线。

### 5.7 `SandboxAuditMiddleware`（Bash 安全审计）

**职责**：所有 `bash` 工具调用先经过它 —— **高危命令拦截、可疑命令告警、全量审计日志**。

**Hook**：`wrap_tool_call` / `awrap_tool_call`。

**实现要点**：
- 三级分类：`block` / `warn` / `pass`。
- **高危模式**（部分节选）：
  - `rm -rf /` 类根目录破坏
  - `curl url | bash`、`base64 -d | ...`、`` `$(curl ...)` ``、`>` 到系统目录 / 启动脚本
  - `/dev/tcp/`（bash 内建网络绕过）、`LD_PRELOAD=`、fork bomb `:(){ :|:& };:`
  - 直接使用 `tosutil` 也被拦截（AIO 里必须走 `tos_storage` 工具）
- **`/mnt` 写入保护**：只有 `/mnt/uploads`、`/mnt/state`、`/mnt/manifests` 三个前缀可写；对 `chmod / cp / rm / tar / touch` 等 write-like 命令严格审查目标路径。
- **复合命令解析**：`_split_compound_command` 手写一个感知引号 / 转义的 tokenizer，把 `cmd1 && cmd2 ; cmd3` 拆开逐条分类，同时也用整串扫一次（防止跨语句结构性攻击，例如 `while true; do bash & done`）。
- **审计日志**：每次都写一条 JSON `{timestamp, thread_id, command, verdict}` 到标准 logger，命令过长时截断到 200 字符。
- **中危命令**（`pip install`、`sudo`、`chmod 777`、`PATH=`）执行**成功后**在 ToolMessage 末尾追加 `⚠️ Warning:` 提示，让 LLM 意识到副作用。

**场景**：由于 tob_audit_agent 项目名字就叫「审计」，且沙箱本身可能对宿主机资源有较高权限，SandboxAuditMiddleware 是**沙箱最后一道防线**，也是命名对齐产品定位的核心组件。

### 5.8 `ToolProgressMiddleware`（工具执行进度流事件）

**职责**：为每次工具调用向前端流式发出 `tool_call_start` / `tool_call_end` 自定义事件，供 Feishu 频道或 Web UI 实时渲染"正在执行 bash: `ls -la ...`（1.2s）"面板。

**Hook**：`wrap_tool_call` / `awrap_tool_call`。

**实现要点**：
- 事件字段：`tool_name`、`tool_args_preview`（bash 直接展 `command`，其他工具展 `json.dumps(args)`，最大 500 字符）、`tool_call_id`、`duration_ms`、`is_error`、`status`。
- Bash 专属元数据：从 `BASH_TOOL_METADATA` contextvar 拿 `exit_code`，或从输出末尾正则 `Exit Code: N` 兜底；退出码非 0 时把 `is_error` 置 True。
- Stream writer 三级 fallback：`request.runtime.stream_writer` → `get_stream_writer()` → 静默丢弃（Gateway / 后台任务里没有 writer 是合法情况）。

### 5.9 `ToolErrorHandlingMiddleware`（工具异常兜底）

**职责**：把工具函数里抛出的任意异常吞成一个 `status="error"` 的 `ToolMessage`，让主循环可以继续。

**Hook**：`wrap_tool_call` / `awrap_tool_call`。

**实现要点**：
- 调 handler 前先做**参数完整性检查** `_pre_handler_error`：读取工具的 Pydantic `model_fields`，比对 `is_required()`，如果模型输出的 `args` 缺少必填字段（通常是 tool_call 参数在传输中被截断了），直接返回一条"参数被截断，请重试或拆分内容"的用户友好 ToolMessage —— 避免让 LangGraph 内部把 `ValidationError` 又转成一条隐蔽的 error ToolMessage。
- 捕获异常时保留 `GraphBubbleUp`（LangGraph 的 interrupt/pause 信号）不被吞。
- 错误详情通过 `format_aio_user_error` 优先取沙箱自定义的用户可读消息，最长截到 500 字符。

### 5.10 `OwnerSkillsMiddleware`（每次调 LLM 重建 System Prompt）

**职责**：在每一次 LLM 调用之前，从 Owner Skill Store 读取当前用户开启的 skills 快照，重新渲染 system prompt 并覆盖 `request.system_message`。

**Hook**：`wrap_model_call` / `awrap_model_call`。

**实现要点**：
- 通过 `apply_prompt_template(agent_name, available_skills, owner_skill_snapshot)` 组合模板。
- 显式把 `request.runtime.stream_writer` 传进 `store.snapshot(...)`，因为首次冷启动 acquire 会通过 `asyncio.to_thread` 卸载，此时 contextvar-based 的 stream writer 可能不可用，必须显式携带。
- 出错时不打断整个 run，而是返回一条 assistant-facing 的 `AIMessage`，把错误原因（如"沙箱冷启动失败"）告诉用户。

**场景**：Aegis 支持用户在 Web 端动态开关 skills、导入 Feishu / GitHub 上的自定义 skills；系统 prompt 因此必须是"每次调用重新计算"，不能一次性写死在 agent 定义里 —— 这正是 `wrap_model_call` 而非 `before_agent` 的原因。

### 5.11 `AegisSummarizationMiddleware`（历史摘要 + Skill 救援）

**职责**：当消息历史 token 超过阈值时，用小模型总结前半段，替换成一条 summary 消息；同时确保"最近加载过的 skill 文件"不会被总结掉。

**Hook**：`before_model` / `abefore_model`（继承自 LangChain `SummarizationMiddleware`，在其之上强化）。

**核心增强点**：
- **Trim 修正**：父类 `trim_messages` 强制 `start_on="human"`，但 Aegis 的 system prompt 是在 `OwnerSkillsMiddleware` 里动态注入的，切片开头未必是 HumanMessage，会导致 trim 返回空 → 触发"amnesia"回退。此处改用 `strategy="last"`, `allow_partial=True`, `include_system=True`，并在返回空时兜底为 `messages[-15:]`。
- **Skill 救援**：识别 "读过 `$HOME/.aegis/skills/...` 或 `/home/tiger/.aegis/skills/...` 下文件" 的 read_file / read / view / cat tool_call 与配对 ToolMessage，把最近的 N 个（默认 5 个，总 25k tokens 上限）**从摘要范围里挑出来放进 preserved**。避免把"如何使用某个 skill"的关键说明摘掉。
- **Hook 分发**：在真正摘要前触发 `BeforeSummarizationHook`，供外部注册"总结前存档到 KV / 写日志"之类的副作用。

**场景**：当 audit 类任务需要连续处理几十步工具、上下文轻松破 100k token 时，此中间件让 Agent 依然能沿用早期 skill 文档，而不是每次都重新加载。

### 5.12 `TodoMiddleware`（计划模式增强）

**职责**：继承 LangChain 官方 `TodoListMiddleware`，加上两项 Aegis 自研强化：**上下文丢失自愈** + **提前退出阻断**。

**Hook**：`before_model` / `after_model`。

**实现要点**：
- **上下文丢失检测**（`before_model`）：如果 state 里的 `todos` 非空，但 `write_todos` 的 AIMessage 已经被 summarization 掉了、且没有 `todo_reminder`，就注入一条 `<system_reminder>` HumanMessage 把当前 todos 复述给模型。
- **提前退出阻断**（`after_model`）：如果模型最后一条 AI 消息没有 `tool_calls`（想退出）但还有未完成的 todo，注入 `todo_completion_reminder` 并 `jump_to="model"` 强制回到模型节点。有 `_MAX_COMPLETION_REMINDERS = 2` 的上限防止死循环。
- 只有在 `_create_todo_list_middleware(is_plan_mode=True)` 也就是用户显式启用计划模式时才会注册。

### 5.13 `TokenUsageMiddleware`（用量日志）

**职责**：从最后一条 AIMessage 的 `usage_metadata` 抓 input/output/total token 数，打 info 日志。

**Hook**：`after_model` / `aafter_model`。

**实现要点**：文件仅 37 行，就是一层极薄的 logger 包装。之所以做成独立中间件而非嵌在业务代码里，是因为它可以通过 `get_app_config().token_usage.enabled` **开关式加载**。

### 5.14 `TitleMiddleware`（自动生成标题）

**职责**：在首轮 user↔assistant 交换完成后，用一个轻量模型（可配置，未配置就用默认）生成一个不超过 N 字的会话标题，写进 state 的 `title`。

**Hook**：`after_model` / `aafter_model`。

**实现要点**：
- 同步版仅生成 fallback title（截取用户首条消息的前 50 字），异步版才真正调 LLM。
- 支持配置 `title_config.model_name`、`max_words`、`max_chars`、`prompt_template`。
- 自动剥离 DeepSeek-R1 / MiniMax 之类推理模型的 `<think>...</think>` 段。

### 5.15 `ViewImageMiddleware`（视觉模型专用）

**职责**：当模型调用了 `view_image` 工具且所有 tool_call 都已经完成时，在下一次 LLM 调用前**主动追加一条包含 base64 图片内容的多模态 HumanMessage**，让模型"真正看到"图片。

**Hook**：`before_model` / `abefore_model`。

**实现要点**：
- 判断条件严格：最后一条 AIMessage 有 `view_image` tool_call → 后续所有 tool_call_id 都有配对的 ToolMessage → 之后还没有相同图片说明块 → 才注入。
- 内容格式：`[{"type":"text","text":"Here are the images..."}, {"type":"image_url","image_url":{"url":"data:mime;base64,..."}}]`，与 OpenAI / Anthropic 视觉 API 兼容。
- 只有当 `model_config.supports_vision` 为 True 才被 `_build_middlewares` 注册。

### 5.16 `LoopDetectionMiddleware`（循环破除）

**职责**：观察每一次 AIMessage 里的 tool_calls 组合，识别"同一组调用参数反复出现"和"某工具类型被高频调用"两种循环，超过阈值先告警后硬停。

**Hook**：`after_model` / `aafter_model`。

**实现要点**：
- **两层探测**：
  1. **Hash 层**：对每次的 tool_calls multiset 归一化后 MD5 取前 12 位。滑动窗口 40，同 hash 连续 5 次 → 注入 `[LOOP DETECTED] ...` HumanMessage（每 hash 只警一次）；连续 8 次 → 直接把最后一条 AIMessage 的 `tool_calls` 清空 + 追加 `[FORCED STOP] ...` 文本，强制模型走 END。
  2. **频次层**：每个 `tool_name` 累计到 60 → 警告；到 100 → 硬停。抓的是"读 40 个不同文件的死循环"这种 hash 层看不到的模式。
- **稳键提取**（`_stable_tool_key`）：
  - `read_file` 只取 `path` + 行区间桶（每 200 行一桶），忽略微小行号扰动。
  - `write_file` / `str_replace` 对内容敏感 → 哈希完整 args 减少误杀。
  - 通用工具（bash / grep / glob）用 `path/url/query/command/pattern/glob/cmd` 白名单字段。
- **LRU 保护**：`OrderedDict` 追踪最多 100 个 thread，超过就淘汰最旧。
- **告警注入**：用 `HumanMessage` 而非 `SystemMessage`，因为 Anthropic 只允许 system 出现在对话开头，中途 system 会导致 `_format_messages()` 崩溃。

**场景**：Agent 陷入"读同一段文件 → 又读一次"的常见死循环时，此中间件是最后的 P0 兜底。

### 5.17 `ClarificationMiddleware`（澄清拦截，链尾）

**职责**：识别模型调用 `ask_clarification` 工具的意图，拦截它，把问题格式化后作为 ToolMessage 返回，并**用 `Command(goto=END)` 直接结束当前图**——把控制权交回给用户。

**Hook**：`wrap_tool_call` / `awrap_tool_call`。

**实现要点**：
- 只在 `request.tool_call["name"] == "ask_clarification"` 时才劫持，其他工具透传。
- 支持五种 clarification 类型（`missing_info` / `ambiguous_requirement` / `approach_choice` / `risk_confirmation` / `suggestion`），每种用不同 emoji（`❓🤔🔀⚠️💡`）。
- 稳定 `id = clarification:{tool_call_id}` —— 让**重试**的 clarification 请求（因为幂等）覆盖之前那条，不会在历史里叠加。
- 兼容 Qwen3-Max 之类会把数组序列化成 JSON 字符串的模型，主动 `json.loads`。

**为什么放最后**：其它中间件都可能包 wrap_tool_call，如果 ClarificationMiddleware 不在最外层，`ask_clarification` 就会先走进 audit / progress / error 中间件，产生多余事件。放在链尾意味着它是"第一个看到" tool_call、"第一个决定短路"的一层。

## 六、协同应用示例：一次典型任务里的中间件链路

设想 tob_audit_agent 面对如下用户请求：

> **用户**：（上传 `财报.pdf`）「请审计这份财报里的关联交易披露是否合规。」

按照上文的装配顺序，一次 run 里的中间件事件流大致如下：

1. **`ThreadDataMiddleware.before_agent`**：解析 `thread_id`，把路径写进 `thread_data`，并在 HumanMessage 最前面加 `<session thread_id="t-abc"/>`。
2. **`OwnerActivityMiddleware.abefore_agent`**：向 Owner Sandbox Registry `begin("agent_run", ...)`，开一枚心跳 task。
3. **`UploadsMiddleware.abefore_agent`**：从 `additional_kwargs.files` 拿到 `财报.pdf`，抽出 `.md` 大纲，在 HumanMessage 开头插入 `<uploaded_files>...` block。
4. **`SandboxMiddleware`**（lazy）：暂不做事，等第一次 bash 调用触发。
5. `create_agent` 内部进入首轮，先跑 `before_model`：
   - **`AegisSummarizationMiddleware.abefore_model`**：token 不足阈值，直接跳过。
   - **`ViewImageMiddleware.abefore_model`**：还没有 view_image，直接跳过。
6. 进入 `wrap_model_call` 链：
   - **`DanglingToolCallMiddleware.awrap_model_call`**：历史无悬挂 tool_call，透传。
   - **`LLMErrorHandlingMiddleware.awrap_model_call`**：检查熔断器（closed），调下一层。
   - **`OwnerSkillsMiddleware.awrap_model_call`**：从 Owner Skill Store 拉快照，重新渲染 system prompt（此时会把 audit-domain skill 的说明拼进 prompt），覆盖 `request.system_message`。
7. 模型返回一个 tool_call：`bash("pdftotext /mnt/uploads/财报.pdf ...")`。进入 `after_model`：
   - **`TokenUsageMiddleware`**：打一行 `LLM token usage: input=... output=...`。
   - **`TitleMiddleware`**：这是首轮完成，异步调小模型生成标题「财报关联交易合规审计」。
   - **`LoopDetectionMiddleware`**：hash 首次出现，`count=1`，无动作。
8. 进入 `wrap_tool_call` 链：
   - **`SandboxAuditMiddleware.awrap_tool_call`**：命令 `pdftotext ...` 分类为 `pass`，写审计日志。
   - **`ToolProgressMiddleware.awrap_tool_call`**：向 stream_writer 发 `tool_call_start` 事件（前端弹出 bash 面板）。
   - **`ToolErrorHandlingMiddleware.awrap_tool_call`**：预校验参数完整性，通过后调 handler。
   - **`ClarificationMiddleware.awrap_tool_call`**：name 不是 `ask_clarification`，透传。
9. 沙箱首次工作 → `SandboxMiddleware` 触发 lazy acquire → `pdftotext` 执行完毕返回 ToolMessage。
10. 中间件链反向出栈：`ToolProgressMiddleware` 发 `tool_call_end`（含 `exit_code=0`、`duration_ms=812`）。
11. 若过程中模型触发 `ask_clarification("你希望我把重点放在关联方 A 还是 B 的披露上？")`，**`ClarificationMiddleware`** 直接返回 `Command(goto=END)`，前端展示两个候选按钮 —— 整个 run 暂停等用户回答。
12. 若累计到几十轮后 token 逼近上限，`AegisSummarizationMiddleware` 出手：识别最近调用过 `audit-checklist` skill 的读取记录，把这批 tool_call/ToolMessage 从摘要范围里保留下来，其它前半段消息用小模型压缩成一条 summary。
13. 若模型陷入"读同一个 PDF 段落 5 次"的循环，`LoopDetectionMiddleware` 先注入警告；到 8 次直接清空 `tool_calls`，把最终答复强制交给模型。
14. 整个 run 结束 → `OwnerActivityMiddleware.aafter_agent` 取消心跳、释放活跃标记。

## 七、可以从中提炼的设计要点

1. **单一职责 + 组合优先**：每个中间件只做一件事，`_build_middlewares()` 用一段线性代码把它们串成链条；替换或删掉某一层不影响其他层。
2. **顺序即契约**：装配顺序不是审美选择，而是"谁先写 state / 谁修补历史 / 谁最后拦截"的**依赖协议**。`lead_agent/agent.py` 顶部注释把顺序理由写得清清楚楚，这是任何后续修改都必须遵守的约束。
3. **同步 + 异步双实现**：所有 hook 都同时实现 `xxx` 与 `axxx` 版本，方便本地 TUI 同步执行与 Gateway 异步流式执行两种模式共用同一套中间件。
4. **回退与静默失败**：如 `stream_writer` 缺失、TitleMiddleware 调 LLM 失败、Skill 快照拉取失败，都设计成"降级 / 静默"而不是"整个 run 崩掉"，让 Agent 在部分子系统故障时依然可用。
5. **观察即副作用**：TokenUsage / SandboxAudit / ToolProgress 三层是纯观察者，返回值都是 `None` 或原样透传，唯一的输出是 logger 与 stream event。这让"观察层"可以在生产环境按需开关。
6. **通过 `Command(goto=..., jump_to=...)` 影响图流向**：`ClarificationMiddleware(goto=END)`、`TodoMiddleware(jump_to="model")` 都通过 LangGraph 的 Command 机制干预图，而不是直接改 state 里的消息。这是 LangGraph 中间件与传统「拦截器」最大的区别。
7. **状态扩展靠 TypedDict + `NotRequired`**：每个中间件都定义自己的 `<Name>State`，用 `NotRequired[dict|None]` 把新字段合并进 AgentState，既保留类型提示又允许字段缺失。
8. **测试可分层**：`backend/tests/` 下每个中间件都有独立测试（`test_clarification_middleware.py`、`test_loop_detection_middleware.py`、`test_summarization_middleware.py` 等 15 个 middleware 相关测试文件），进一步印证单一职责与低耦合。

## 八、扩展指引：如何在 tob_audit_agent 里新增一个中间件

以「审计报告水印注入」为例，若希望在每次 LLM 生成审计报告的最终 AIMessage 中追加水印文本，可以：

1. 在 `backend/packages/harness/aegis/agents/middlewares/` 下新建 `audit_watermark_middleware.py`：

   ```python
   from typing import override
   from langchain.agents import AgentState
   from langchain.agents.middleware import AgentMiddleware
   from langchain_core.messages import AIMessage
   from langgraph.runtime import Runtime

   _WATERMARK = "\n\n---\n本报告由 Aegis Audit Agent 自动生成，仅供参考。"


   class AuditWatermarkMiddleware(AgentMiddleware[AgentState]):
       @override
       def after_model(self, state: AgentState, runtime: Runtime) -> dict | None:
           messages = state.get("messages", [])
           if not messages:
               return None
           last = messages[-1]
           if not isinstance(last, AIMessage) or last.tool_calls:
               return None  # 非终局消息不加水印
           if _WATERMARK in (last.content or ""):
               return None
           patched = last.model_copy(update={"content": (last.content or "") + _WATERMARK})
           return {"messages": [patched]}
   ```

2. 在 `_build_middlewares()` 的 `custom_middlewares` 位点或直接 `middlewares.append(AuditWatermarkMiddleware())` 处注册。选择位置的原则：**观察类中间件放靠近尾部、拦截类靠近尾部但必须在 ClarificationMiddleware 之前**。

3. 为它写单测（可参考 `tests/test_title_middleware_core_logic.py` 的骨架），确保：
   - 无消息 → None
   - 最后一条不是 AIMessage → None
   - 最后一条有 tool_calls（还没到终局）→ None
   - 已经带水印 → 幂等
   - 正常终局消息 → 追加水印

这就是 Aegis 中间件体系"新增一层"的完整成本 —— **一个文件 + 一处注册 + 一份测试**。

## 九、总结

Aegis 的中间件体系围绕 LangChain `AgentMiddleware` 的五个 hook 点，把"上下文、可靠性、可观测性、安全、交互"五类横切关注点拆分成 17 个单一职责的小类，通过 `lead_agent/agent.py` 的 `_build_middlewares()` 编排成一条严格有序的链。它带来的收益是：

- **业务逻辑保持极薄**：`agent.py` 只关心"选模型 / 选工具 / 装 prompt / 装中间件"，具体行为改造几乎全部落到中间件里。
- **横切能力可以增量演进**：熔断、循环检测、Skill 救援这些复杂特性都是在原有链上"加一层"而非重构主流程。
- **可观测与安全成为默认能力**：所有 bash 命令都被审计、所有 LLM 抖动都会重试、所有工具执行都有进度事件、所有循环都会被兜底 —— 无需业务代码显式调用。

在 tob_audit_agent 这个「面向审计场景」的落地里，`UploadsMiddleware` 提供文件感知、`SandboxAuditMiddleware` 提供合规底线、`AegisSummarizationMiddleware` 支撑长时段审计任务、`ClarificationMiddleware` 支撑与审计人员的多轮澄清、`LoopDetectionMiddleware` 兜底自动化审计的循环风险 —— 所有能力共同构成了一个"稳定、可控、可解释"的 Agent 运行时。
