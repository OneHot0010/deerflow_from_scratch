# 飞书（Feishu / Lark）接入设计与实现详解

> 本文以 `tob_audit_agent` 项目（Aegis Agent 平台）为例，系统梳理其"从飞书用户消息到 Agent 执行结果回传"的完整链路。
> 涉及的核心目录：`backend/app/channels/`，其中 Feishu 专属实现位于 `backend/app/channels/feishu/`。

---

## 1. 总览：Aegis 的 Channel 抽象

Aegis 使用一套**可插拔的 IM Channel 系统**统一接入外部 IM 平台，飞书是目前唯一启用的 Channel。整体分层如下：

```
外部 IM 平台 (飞书 WebSocket)
        │  lark-oapi ws.Client
        ▼
┌────────────────────────────┐
│  FeishuChannel              │  ← 平台适配层：协议解析、卡片渲染、文件上下行
│  (channels/feishu/*.py)     │
└──────────────┬──────────────┘
               │ InboundMessage / OutboundMessage
               ▼
        MessageBus (asyncio.Queue)
               │
               ▼
┌────────────────────────────┐
│  ChannelManager             │  ← 统一调度：并发、线程、路由到 LangGraph
│  (channels/manager.py)      │
└──────────────┬──────────────┘
               │ langgraph-sdk
               ▼
        LangGraph Server (Aegis Agent)
```

关键抽象：

- **`Channel`（`channels/base.py`）**：所有 IM 通道的抽象基类，定义 `start / stop / send / send_file / receive_file / resolve_file_staging / update_card_status` 等生命周期与消息 API。
- **`MessageBus`（`channels/message_bus.py`）**：进程内异步消息总线，解耦 Channel 与 Manager。
- **`ChannelManager`（`channels/manager.py`）**：消费 InboundMessage，创建/复用 LangGraph 线程，把 Agent 输出以流式方式回写到 Channel。
- **`ChannelService`（`channels/service.py`）**：读取 `config.yaml` 中的 `channels` 配置，按需实例化并启动各 Channel。

Channel 注册表使用**懒加载导入路径**，避免未安装 `lark-oapi` 时导入失败：

```python
# backend/app/channels/service.py
_CHANNEL_REGISTRY: dict[str, str] = {
    "feishu": "app.channels.feishu:FeishuChannel",
}
_CHANNEL_CREDENTIAL_KEYS: dict[str, list[str]] = {
    "feishu": ["app_id", "app_secret"],
}
```

## 2. 配置与启动

### 2.1 配置文件 `config.yaml`

飞书配置位于顶层 `channels.feishu` 节点：

```yaml
channels:
  max_concurrency: 20       # 全通道并发上限
  session:                  # 各 Channel 共享的默认 Agent 会话参数
    assistant_id: lead_agent
    config: { recursion_limit: 1000 }
    context: { thinking_enabled: true, is_plan_mode: false }

  feishu:
    enabled: true
    streaming: true
    app_id: $FEISHU_APP_ID          # 从环境变量注入
    app_secret: $FEISHU_APP_SECRET
    domain: https://open.feishu.cn  # 国内；国际版为 open.larksuite.com
    cardkit:
      max_card_elements: 100        # 单卡元素上限，触发卡片轮转
      rotation_enabled: true
```

对应 `.env.example` 提供了 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 的占位。`app_secret` 会被登记到日志脱敏名单（`gateway/app.py:54-58`），避免明文外泄。

### 2.2 服务启动流程 `gateway/app.py`

在 FastAPI 的 lifespan hook 里启动通道服务：

```python
# backend/app/gateway/app.py
from app.channels.service import start_channel_service
channel_service = await start_channel_service()
```

`ChannelService.start()` 会：
1. 启动 `ChannelManager`（连接 LangGraph Server）。
2. 遍历 `channels` 配置节点，`enabled=true` 且提供了 `app_id/app_secret` 的通道被 `_start_channel()` 实例化。
3. 通过 `resolve_class(import_path)` 反射加载 `FeishuChannel`，注入 `bus` 与 `store`，然后调用 `channel.start()`。

如果只填了凭据但未 `enabled: true`，会打印告警提示，避免"配了但没生效"的隐性错误。

## 3. FeishuChannel：接入层核心

`FeishuChannel`（`channels/feishu/channel.py`，约 1839 行）是飞书接入的主实现。它选择了**长连 WebSocket 模式**（`lark-oapi` 的 `ws.Client`），因此**部署机器无需公网 IP**，特别适合企业内网 / Serverless 场景。

### 3.1 SDK 惰性导入：`_LarkApiTypes`

为了让"未装 `lark-oapi` 时也能 import 模块"，所有 lark SDK 类型都用 `_LarkApiTypes.from_import()` 惰性加载并归并到一个 dataclass 里：

```python
@dataclass
class _LarkApiTypes:
    lark: Any
    CreateMessageRequest: Any
    ReplyMessageRequest: Any
    CreateMessageReactionRequest: Any
    GetMessageResourceRequest: Any
    PatchMessageRequest: Any
    CreateFileRequest: Any
    CreateImageRequest: Any
    GetUserRequest: Any
    # …
    @classmethod
    def from_import(cls) -> _LarkApiTypes | None:
        try:
            import lark_oapi as lark
            from lark_oapi.api.contact.v3 import GetUserRequest
            from lark_oapi.api.im.v1 import (...)
        except ImportError:
            return None
```

若 `from_import()` 返回 `None`，`start()` 会打印 `"lark-oapi is not installed. Install it with: uv add lark-oapi"` 并优雅降级为不启动。

### 3.2 WebSocket 事件循环隔离

`lark-oapi` 的 `Client.start()` 会调用 `loop.run_until_complete()`，而 FastAPI 使用 uvloop 时主循环已经在运行，直接调用会抛 `RuntimeError`。项目的解决办法是**为 WebSocket 建独立线程 + 新 asyncio 事件循环**，并**手动打补丁替换 SDK 内部的模块级 loop**：

```python
def _run_ws(self, app_id, app_secret, domain):
    loop = asyncio.new_event_loop()
    asyncio.set_event_loop(loop)
    import lark_oapi as lark
    import lark_oapi.ws.client as _ws_client_mod
    _ws_client_mod.loop = loop        # 覆盖 SDK 捕获的旧 loop

    event_handler = (
        lark.EventDispatcherHandler.builder("", "")
        .register_p2_im_message_receive_v1(self._on_message)
        .register_p2_card_action_trigger(self._on_card_action)
        .register_p2_im_message_message_read_v1(self._ignore_event)
        .register_p2_im_message_reaction_created_v1(self._ignore_event)
        .register_p2_im_message_reaction_deleted_v1(self._ignore_event)
        .register_p2_im_chat_access_event_bot_p2p_chat_entered_v1(self._ignore_event)
        .build()
    )
    ws_client = lark.ws.Client(app_id=app_id, app_secret=app_secret,
                                event_handler=event_handler, domain=domain, ...)
    ws_client.start()
```

- WebSocket 线程通过 `asyncio.run_coroutine_threadsafe()` 把入站消息投递回主事件循环。
- 关闭时 `stop()` 会 `join(timeout=5)` 收尾。

### 3.3 订阅的飞书事件

只订阅两类**主动消费**的事件；其余用 `_ignore_event` 显式 ACK，避免 SDK 因未处理事件而告警：

| 事件 | 处理器 | 用途 |
|------|--------|------|
| `im.message.receive_v1` | `_on_message` | 接收用户消息 |
| `card.action.trigger`   | `_on_card_action` | 处理卡片按钮回调（如反馈👍/👎、后台 Job 继续） |
| `message.read_v1`       | `_ignore_event`   | 忽略 |
| `message.reaction_*`    | `_ignore_event`   | 忽略（自己加的 reaction 会被推回） |
| `chat.access.event.bot_p2p_chat_entered_v1` | `_ignore_event` | 忽略 |

订阅接收消息事件所需的飞书应用权限（详见 `docs/backend/FEISHU_MESSAGE_RECEIVE_API.md`）：

- `im:message.p2p_msg:readonly` — 单聊消息
- `im:message.group_at_msg:readonly` — 群里 @机器人
- `im:message.group_at_msg.include_bot:readonly` — 含机器人 @

## 4. 入站消息处理链路

### 4.1 `_on_message`：原始事件解析

WebSocket 线程收到消息后进入 `_on_message(event)`：

1. **抽取标识**：`chat_id`、`msg_id`、`sender.open_id`、`root_id`、`parent_id`。
2. **解析 `content`**：飞书 `content` 是 JSON 字符串，按 `msg_type` 分支：
   - `text` → 直接取文本。
   - `file` / `media` → 抽出 `file_key`，text 用占位符 `[file]` / `[video]`。
   - `image` → 抽出 `image_key`，text 用 `[image]`。
   - `post` 富文本 → 递归遍历 `content` 段落数组，把 `text` / `at` / `a` / `img` / `file` / `media` 段拼接为纯文本，同时收集 file/image key。
3. **@ 群提及过滤**：`_is_feishu_all_mention(content)` 检测 `@所有人 / @_all` 并直接丢弃，避免 bot 响应群公告。
4. **@ 提及归一化**：`_normalize_mentions()` 把 lark SDK 的 `mentions` 对象扁平化为 `{key, name, user_id, open_id, union_id}`；`_replace_mention_placeholders()` 把消息中 `@_user_N` 占位替换成人类可读文本。
5. **命令识别**：以 `/` 开头且属于 `KNOWN_CHANNEL_COMMANDS`（如 `/new`、`/status`、`/stop`）时，`msg_type=COMMAND`，否则 `CHAT`。
6. **构造 `InboundMessage`**：
   ```python
   inbound = self._make_inbound(
       chat_id=chat_id, user_id=sender_id, text=text,
       msg_type=msg_type, thread_ts=msg_id,
       files=files_list,
       metadata={"message_id": msg_id, "root_id": root_id,
                 "parent_id": parent_id, "mentions": mentions},
   )
   inbound.topic_id = None   # 关键：飞书话题不分裂 Aegis 线程
   ```
7. **跨线程投递**：`asyncio.run_coroutine_threadsafe(self._prepare_inbound(msg_id, inbound), self._main_loop)`。

**Thread 收敛设计**：飞书的 `topic_id`（话题回复）**不用于**派生新的 Agent 线程。所有 `(channel, chat_id, user_id)` 的消息共享同一个 Aegis 线程，理由是**沙箱是按 owner-key 绑定的**，按 topic 分线程反而会破坏沙箱复用。

### 4.2 `_prepare_inbound`：入站预处理

在主事件循环里做异步预处理：

1. **富化 @ 提及**：`_enrich_mentions_for_text()` 用 tenant_access_token 通过 `/open-apis/contact/v3/users/{open_id}` 查询企业邮箱前缀，并附加到 mention 上（缓存 6h）。这样 Agent prompt 中能看到人类可读的 @ 名字而不是纯 open_id。
2. **父消息文件解析**：若 `parent_id` 存在但当前消息无文件，调用 `_resolve_parent_files(parent_id)`：
   - 通过 `im.v1.message.get` 拉取父消息 body。
   - `_extract_files_from_content()` 从父消息里再次抽出 file_key/image_key。
   - 结果 merge 到 `inbound.files`。
   这样支持"引用一条含文件的消息 + @机器人 帮我总结"。
3. **加"OK"表情**：非命令消息立即通过 `im.v1.message_reaction.create` 加 表情，缓存 `reaction_id`。
4. **建立运行中卡片**：`_ensure_running_card_started(msg_id, inbound=inbound)`，异步创建"思考中..."流式卡片作为回复位（除文件暂存指令外）。
5. **投递到总线**：`await self.bus.publish_inbound(inbound)`。

### 4.3 文件暂存：`resolve_file_staging`

`ChannelManager` 在把 InboundMessage 交给 Agent 前，会先调 `channel.resolve_file_staging(msg)`。飞书通道的实现（`channel.py:1183`）：

- 用户发送 `+`（可带文件）→ 命中 `_STAGING_TEXTS = {"+", "[file]", "[image]", "[video]"}` → 文件进入 `FileStagingManager`（TTL 10 分钟，持久化到本地 JSON），发反馈"已暂存 N 个文件"，**不进入 Agent**。
- 非暂存指令且暂存区有内容 → 合并 staged files 到当前 msg，继续投递给 Agent。
- 暂存过期 → 追加提示"之前暂存的文件已过期，请重新添加"。

### 4.4 文件下载：`receive_file`

Agent 消费消息前，`ChannelManager` 调 `channel.receive_file(msg, thread_id)` 完成**飞书 → 沙箱**的文件搬运：

1. 对每个 file_key/image_key，调 `im.v1.message_resource.get` 拿到二进制流。
2. 目标位置由沙箱 provider 决定：
   - AIO Sandbox（远程） → `put_upload_stream_async(acquire_context, stream, filename)`，落到沙箱的 `/mnt/uploads/`，返回 sandbox 内部虚拟路径。
   - 本地 fallback → 落到 `sandbox_uploads_dir(thread_id) / filename`。
3. 把 `msg.text` 中的 `[file]/[image]/[video]` 占位符替换成实际虚拟路径，Agent 就能直接读文件。
4. 未匹配到占位符（如来自 parent 消息）的文件走 `msg.metadata["downloaded_files"]`，供 `UploadsMiddleware` 组装成 `additional_kwargs.files`。
5. `metadata["receive_all_ok"]` 标识全部下载成功，决定是否清空暂存区。

## 5. 出站消息：流式卡片渲染

飞书 Channel 的核心亮点是**基于 CardKit 的流式卡片**——用户看到的不是"来一段发一条"，而是**一张会实时增长**的交互卡片，包含"思考过程折叠面板 + 最终答复面板"。

### 5.1 CardKit 卡片结构

由 `feishu/cardkit.py` 定义：

```
┌─ Process (collapsible_panel, expanded) ────────────────┐
│  [collapsible] thought    ← reasoning_content          │
│  [collapsible] bash       ← tool_call                  │
│  [collapsible] thought    ← more reasoning             │
│  [collapsible] ls         ← another tool_call          │
└─────────────────────────────────────────────────────────┘
┌─ Answer (collapsible_panel, lazily created) ────────────┐
│  assistant answer                ← main_content         │
└─────────────────────────────────────────────────────────┘
```

- **Process 面板**：装 reasoning、tool_call、tool_result 等中间过程，每一步是一个可折叠子面板，图标由 `TOOL_ICON_TOKENS` 映射（`bash` → `platform_outlined`，`search` → `doc-search_outlined` 等）。
- **Answer 面板**：懒创建，仅当有最终答案文本才出现，`main_content` 采用 CardKit 的**流式追加 API**逐 token 更新。

关键封装类：

- `CardSession`（dataclass）：单张卡片的运行时状态，含 `card_id`、`element_count`、序号发生器 (`next_sequence`)、各 element_id 池。
- `FeishuCardKitManager`：调用 `lark_oapi.api.cardkit.v1.*` 的 `id_convert / settings / card_element.create / patch / delete` 等 API。
- `CardkitStreamingManager`（`feishu/card_streaming.py`）：把 OutboundMessage 序列化为有序事件（`reasoning / text / trace_text / tool`）投入 `CardkitFlushBuffer`，后台 `_flush_worker` 按最小时间间隔与最小字符阈值合并 / 采样后调用 CardKit API。

### 5.2 卡片创建 3 步

`_create_running_card(source_message_id, ...)`：

1. **回复初始卡片**：`_reply_card_with_json(source_msg_id, streaming_card_json)`，在飞书聊天里得到一条 message_id。
2. **ID 转换**：`cardkit.card.id_convert(message_id)` → `card_id`（CardKit 内部标识）。
3. **开启流式模式**：`cardkit.card.settings({"streaming_mode": true, "streaming_config": {...}})`。

任一步失败会自动回退到"普通交互卡（可 patch，但不流式）"。

### 5.3 首帧唤醒横幅

首帧标题受**沙箱状态**驱动（`_detect_wake_banner`）：

- Owner 有 PAUSED 沙箱 → `"欢迎回来，沙箱唤醒中"`（resume）
- Owner 无沙箱 → `"专属沙箱创建中"`（cold create）
- Owner 有 ACTIVE 沙箱 → 中性 `"**Process**"`（warm reuse）

这个信息从 `AioSandboxProvider._coordinator.get_owner_session_state_async(owner_key)` 拿，与 `acquire` 使用同一权威源，避免出现"resume 却显示 create"的错位。

### 5.4 出站分派：`_send_card_message`

`ChannelManager` 发出 `OutboundMessage` 后：

```python
# 优先走 CardKit 流式
if running_card_id and self._cardkit_manager:
    if await self._cardkit_streaming.dispatch_cardkit_message(...):
        if msg.is_final:
            await self._cardkit_streaming.finalize_cardkit_card(...)
            # 移除 OK 表情，加 DONE / GOT 表情
            # 清理 running_card_id / statuses
        return
# CardKit 失败则回退到 legacy patch
await self._update_card(running_card_id, msg.text)
```

若最终 `finalize` 失败（如卡片元素超上限），会兜底 `_reply_card(source_message_id, text)` **另发一条普通卡片**保证用户能看到最终答案。

### 5.5 卡片轮转（Rotation）

飞书单卡元素上限约 200；`FeishuCardKitManager.is_near_limit()` 判断阈值（默认 100，见 `config.yaml`）时触发 `_rotate_card`：

1. 在原卡片写入提示 `"> 内容已切换到下一张续卡，本卡仅保留过程记录。"`
2. 新建续卡（`_create_continuation_card`）继承 reasoning 展示进度。
3. `_running_card_ids[source_msg_id]` 更新为续卡 id，后续 patch 定位到用户当前所看的续卡。

### 5.6 文件回传

Agent 产物（图表、报告、下载文件）通过 `send_file()` 上传：

- 图片 → `im.v1.image.create`（`msg_type=image`，10MB 上限）。
- 文件 → `im.v1.file.create`，按后缀映射 `file_type` (`xls/ppt/pdf/doc/stream`，30MB 上限）。
- 超限时发提示卡片："文件超过飞书发送上限，无法发送。"
- 若消息带 `thread_ts` 就 `reply` 到源消息线程，否则 `create` 到 chat。

## 6. 卡片交互回调

`_on_card_action` 处理 CardKit 卡片的按钮点击（同样在 lark WS 线程里）：

```python
if action_value["kind"] == "answer_feedback":
    # 打分反馈：写 FeedbackStore + 附加 trace_id
    fut = asyncio.run_coroutine_threadsafe(
        self._complete_answer_feedback(action_value, operator_open_id),
        self._main_loop)
    return _toast(ok, message)

continuation_payload = _extract_jobs_continuation_from_action_payload(action_payload)
if continuation_payload is not None:
    # 长时后台 Job 的"继续处理"按钮
    fut = asyncio.run_coroutine_threadsafe(
        _complete_jobs_continuation(continuation_payload), self._main_loop)
```

反馈流程：
1. `attach_answer_feedback` 在 `finalize_cardkit_card` 时把反馈 footer 追加到 Answer 面板，并注册一个 `feedback_token → FeedbackTarget`。
2. 用户点击 → `_complete_answer_feedback` 校验 `operator_open_id == target.user_id`（只能评价自己请求）。
3. 追加一条 `FeedbackRecord` 到 `feedback.jsonl`，并**响应式**（非 pre-emptive，避免 200810 错误）移除按钮。

## 7. 与飞书 OpenAPI 的直接交互

`FeishuChannel` 除了通过 `lark-oapi` SDK 走 WebSocket + 业务 API，还**手动**调了两个 REST 端点用于富化：

```python
_FEISHU_OPEN_API_DOMAIN = "https://fsopen.bytedance.net"
```

| 端点 | 用途 |
|------|------|
| `POST /open-apis/auth/v3/tenant_access_token/internal` | 用 `app_id + app_secret` 换 tenant_access_token（缓存 `expire - 60s`） |
| `GET  /open-apis/contact/v3/users/{open_id}` | 查询用户邮箱，用于 @ 提及富化（结果缓存 6h） |

其它调用（发消息、加表情、上传文件、CardKit）**统一走 SDK**：`im.v1.message.{create,reply,patch,get}`、`im.v1.message_reaction.{create,delete}`、`im.v1.image.create`、`im.v1.file.create`、`im.v1.message_resource.get`、`contact.v3.user.get`、`cardkit.v1.card.{id_convert,settings}`、`cardkit.v1.card_element.{create,patch,delete}`。

Reply API 的请求体协议详见 `docs/backend/FEISHU_MESSAGE_REPLY_API.md`：路径为 `POST /open-apis/im/v1/messages/{message_id}/reply`，`content` 是 JSON 序列化字符串，`msg_type` 为 `text/post/image/file/interactive` 等。

## 8. 用户使用流程（消息交互闭环）

`docs/backend/FEISHU_CHANNEL_GUIDE.md` 从产品视角描述了完整闭环：

| 阶段 | 用户看到 | 系统动作 |
|------|----------|----------|
| 收到消息 | 消息上出现 OK 表情 | `_add_reaction(msg_id, "OK")` |
| 处理中 | 回复一张 "**Process**" 或"沙箱唤醒中"卡片 | `_create_running_card` |
| 推理流式 | Process 面板增长（thought / tool 折叠子面板） | CardKit `append_thought_panel / append_tool_element` |
| 答复流式 | Answer 面板懒创建，`main_content` 打字机式增长 | CardKit `stream_text` |
| 处理完成 | OK 变 DONE，卡片折叠 Process、展开 Answer，末尾出现反馈按钮 | `finalize_cardkit_card` + `attach_answer_feedback` |
| 出错回退 | 若卡片超限，另回复一条普通卡片给出最终答案 | `_reply_card` fallback |

命令消息（`/new`、`/status`、`/stop` 等）**跳过表情反馈**，走 `COMMAND_HANDLERS` 直接返回结果。

## 9. 设计要点小结

1. **平台适配层与业务层解耦**：`Channel` 抽象 + `MessageBus` 让 `FeishuChannel` 只关心飞书协议，`ChannelManager` 只关心 Agent 调度。理论上再接入 Slack/DingTalk 只需实现一个新 Channel 类。
2. **WebSocket 长连**：无需公网 IP，部署在企业内网即可，但需要为 `lark-oapi` 显式打事件循环补丁避开 uvloop 冲突。
3. **CardKit 流式卡片**：单卡承载"思考过程 + 最终答案"，具备**元素上限保护**（rotation）、**冷启动横幅**（wake banner）、**降级路径**（普通交互卡 → 文本回复）。
4. **沙箱一致性**：飞书话题 (topic) **不分裂** Aegis 线程；wake banner 从沙箱 owner-session 状态取，保证 UI 与真实沙箱状态同步。
5. **文件双向搬运**：
   - 入站：`message_resource.get` → AIO 沙箱 `put_upload_stream_async`；支持"引用父消息"、"暂存 + 批量提交"两种交互模式。
   - 出站：图片走 `image.create`，文件走 `file.create`，按后缀映射 `file_type`；大小超限时明确告知用户。
6. **性能与稳定性**：
   - Tenant token / 邮箱前缀均有 TTL 缓存。
   - `send()` 三次指数退避重试（1s/2s/4s）。
   - 卡片流式合并（`CardkitFlushBuffer`）减少 API 调用频率。
   - `_ignore_event` 显式 ACK 无关事件，避免 SDK 告警。
7. **可观测性**：Process 面板本身就是 tool call / reasoning 的可视化 trace；`trace_id + FeedbackStore` 支持将用户反馈关联到具体一轮 Agent 执行，写入 `backend/.aegis/channels/feedback.jsonl`。
